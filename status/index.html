    Status: what is verified, and how¶

    Version 0.9.0 is published as a GitHub release, with an AppImage for Linux and the kit of the ESP32-4848S040; the portable package for Windows is that of 0.7.1, under the old name. This page separates what has been checked from what has only been written.

    Read this first¶

    The project was built broad on purpose: features expected to be useful were included from the start, so that the design would not need to be reopened later. The automated tests are many. Human testing is scarce: few people have used the IDE, and much of what is listed below has never been tried by a person on a real task. Expect rough edges, and treat every "not tried" below as an open question, not as a formality.

    How each area was checked¶

    • Tests: covered by the automated suite, more than 1250 tests.
    • Self-test: exercised in the real IDE window by copper-and-code-studio selftest. Besides, suites run by hand (pytest tests/manual --manual) trigger every menu entry, toolbar button and context menu entry of the IDE in five states, with every dialog answered with Cancel and with OK, look at every dialog in English and Italian, compare pictures of the window, and cause faults such as a full disk or a board pulled out; they check that nothing breaks, not that the result is right. They are not a person using the IDE. How it is tested describes every check and what none of them sees.
    • Board: tried on real hardware, with the board named.
    • Not tried: written and tested by machine only, or not at all.

    Project website¶

    The English documentation, fourteen browser demos and six videos are published at https://copper-and-code.github.io/copper-and-code-studio/ from the gh-pages branch. On 12 November 2026, the public home, manual, gallery, and the five demos of that day were checked in Chromium. Each demo reported a running WebAssembly application and a non-black canvas; a simulated touch changed the Fifteen screen, and no requests went to external domains. The IDE test for Help → Online Documentation also passed and opens the same public address. On 24 November the seven demos added that day (Block Drop, Star Guard, Frog, Orbit, Sandwich Tower, Crossword, Clock) were started in headless Chromium: no errors in the console, and a press on the screen started Block Drop, Frog and Orbit. Examples that need WiFi, the SD card or the board (Forecast, Photo Frame, FTP Server, Settings) are not demos.

    Firefox, Safari, and a real phone with touch and sound have not been tried.

    The IDE in the browser¶

    The whole IDE in the browser is built in copper-and-code-studio-web, a repository of its own that holds this one as a git submodule at a tag and runs its core/, gen/ and build/ in Pyodide. It is published at https://copper-and-code.github.io/copper-and-code-studio-web/. It is a work in progress: experimental, but already usable, in the author's judgement. Its checks are recorded in that repository, not here.

    Known defects and open points¶

    • Windows. The portable package of 0.4 did not start on a real Windows: it bundled a copy of ICU that hid the system's. The package of 0.6.0 is built without it and starts on Windows 11. The self-test run there passed 76 steps of 78. The step that failed was a mistake of the self-test, which compared a path written with \ with the same path written with /; the step after it was skipped. The run also showed a real defect: when the program ended while a measurement was running, a simulator process stayed alive and its temporary folder could not be removed. Both are corrected, and the author ran the corrected package on Windows 11 without that error. Tests under Wine had shown neither. A third defect, reported by the author, is corrected: started from the program file, a console window flashed four times at almost every operation. On 13 November 2026 the author saw no such window with the package of 0.6.1. With a package built on 13 November 2026 from the branch programs-without-pages, the author used a board on a COM port; the window's icon and pinning it to the taskbar did not work. Not looked into yet.
    • The new name, Copper and Code Studio, came with 0.8.0. What was tried, on the author's computer, 20 November 2026: the whole suite, the self-test and the suites run by hand (the monkey in test_save_and_reopen.py crashes the IDE, as it already did with the code before the new name, and one long random sequence of test_random_use.py failed once, but not when it was replayed on its own); an AppImage built under the new name, --version and the self-test from an empty folder (105 steps passed); the settings and a project written by the code of 0.7.2, read by the renamed IDE (language, layout of the panels, recent files and the configuration folder kept, the project saved again byte for byte the same); the three commands. Not tried: the lines the IDE reads back from a board, now beginning with LMS_, on a real board (only on the virtual board and the boards kept in memory by the tests); the Windows packages under the new name, and the installer over an installation of LVGL MPY Studio; the project website at its new address. See The new name.
    • The IDE does not know the pins of a board. A block takes the pin the user types, a number or a name such as PA5, and nothing warns when it is one the display or the memory already uses.
    • The RAM budget shown in the status bar is measured in the 64-bit simulator and is an overestimate for 32-bit boards. The fonts of a project take about their size on both, but on the ESP32-4848S040 LVGL grows its memory in steps of 64 kB, which the budget does not count.
    • Renaming a Python module does not rewrite the code that imports it; the IDE warns.
    • Reference images that hold a changing value fail when the generator changes: the EIM-01 example shows the free memory on a page, and its image had to be regenerated for 0.6.
    • Continuous integration covers tests, not packages. Since the repository became public, each push runs the whole suite and the self-test on Linux, and on Windows the tests of the core, of the runtime and of the IDE, and the self-test. On the Linux machine 72 tests are skipped, because they need what is not built there: the launchers of single-file games, the WebAssembly runtime, Wine, a browser. Packages are built and checked by hand.
    • An upload that sends only what changed is tried on one board, the ESP32-4848S040. Whether the firmware of the other boards has the hashlib it needs is not checked: without it every file is sent, as before.
    • The kit of the ESP32-4848S040 is checked by tests (its content, the firmware checked against the release, the same zip twice) and its card is the one tools/esp32_sd.py writes, tried on the board; a board set up from the kit alone, firmware erased and written again, is not tried yet.

    What is not there¶

    • C on boards: only MicroPython is uploaded. The C export is source code for another project.
    • An online catalogue of blocks, and blocks that depend on other blocks.
    • Extensions that run inside the IDE: blocks are data and MicroPython code, nothing more.
    • Blocks for PWM, ADC, I2C, SPI and UART: planned in the plan, not written.
    • A debugger. Errors are reported with file and line; there are no breakpoints.
    • macOS.

    How to check for yourself¶

    .venv/bin/python -m pytest -q        # the whole suite, about ten minutes
.venv/bin/copper-and-code-studio selftest   # the IDE uses itself, about twenty seconds

    The self-test writes report.txt with one line for each step. A step that fails is a defect worth reporting.
