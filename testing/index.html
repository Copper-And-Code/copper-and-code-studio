    How Copper and Code Studio is tested¶

    Few people have used the IDE so far, so most of the checking is done by machine. This page says what is checked, by what, how to run it, and what no automated check can see. What is verified says, area by area, which of these checks it has had.

    The layers¶

    Check What it is When it runs Time
    Test suite more than 1,380 pytest tests: generation, fuzzing, the runtime, the GUI, the protocol with the board, all the widgets, MicroPython/C pixel parity at each push, in the CI about 11 minutes
    Self-test the real IDE window driven as a person would, through 13 scenarios and 105 steps at each push, in the CI, on Linux and Windows about 30 seconds
    Visual tests the pages of a project compared pixel by pixel with stored pictures, also after touches by hand, per project seconds per page
    Suites run by hand every action and context menu, every dialog, the looks, faults, random use, in tests/manual when someone decides to minutes each
    Board tests tests on a real board only with its owner present
    Use by a person the author, now and then

    Test suite¶

    QT_QPA_PLATFORM=offscreen .venv/bin/pytest -q

    The tests use a temporary configuration folder and never open a real board's port. Boards are replaced by fakes that answer as mpremote or the board's REPL would, and, on Linux, by a virtual board (tests/virtual_board.py): the MicroPython of the runtime behind a pseudo-terminal, which the IDE's board code reaches with the real mpremote and the real raw REPL. Its flash is a folder of the PC it cannot leave; it counts the soft resets, so a test can tell whether an operation restarted the board. Tests that need a built runtime, the Windows cross-compiler or a browser are skipped, and say why, when those are missing.

    Some cheap checks of the looks run here too, in English and in Italian (tests/test_window_checks.py, tests/test_fit_screen.py): no shortcut used twice, no menu with two entries on the same underlined letter, no text cut off and no widgets covering each other in the main window at 1280×800, the window and the large dialogs no larger than the screen, and no text, tooltip or menu entry left in English after switching to Italian.

    The CI (.github/workflows/ci.yml) runs at each push to main and on pull requests. On Linux it runs the whole suite and the self-test; on Windows the parts that depend on the system (the core, the Windows runtime and packages, the GUI) and the self-test. It does not build the packages.

    Self-test¶

    .venv/bin/copper-and-code-studio selftest

    It creates a project, takes widgets from the toolbox, sets properties, types a handler, saves, starts the simulator and touches the screen; other scenarios cover pages, resolution, pictures and fonts, Python modules, the Timer and the Buzzer, errors and hardware blocks, the Files panel and its tabs (open a folder, edit, save, New File and Rename from the panel's menu), programs without pages (Run Program, typing in the terminal; Linux only), Project Settings and board profiles (a profile duplicated in the Profile Manager, then used by the project), and the files of a board (Connect, the board's files in the Files panel, Upload Files, Run File on Board). The board is one the self-test keeps in memory: it answers what the window asks, without the serial protocol, which the test suite covers with its own fakes. See the manual for its options and report.

    Visual tests¶

    copper-and-code-studio test project.json

    The reference pictures live next to the project, in visual/<width>x<height>/. The examples eim-01 and weather have them. See the manual.

    Suites run by hand¶

    tests/manual holds suites too long for every push. They are skipped unless pytest gets --manual, and the CI never runs them:

    QT_QPA_PLATFORM=offscreen .venv/bin/pytest -q tests/manual --manual
QT_QPA_PLATFORM=offscreen .venv/bin/pytest -q tests/manual/test_every_action.py --manual
LMS_PROGRESS=1 QT_QPA_PLATFORM=offscreen .venv/bin/pytest -q -s tests/manual/test_every_action.py --manual   # a line per entry
tools/manual_on_x.sh                         # the self-test and every suite on a real X display
    Suite Time What it checks
    test_every_action.py about 10 minutes every menu entry, toolbar button and context menu entry
    test_every_shortcut.py about 1 minute every keyboard shortcut, pressed with the focus in each place a person has it
    test_every_dialog.py about 6 minutes every dialog, in English and Italian: size, text cut off, Tab, Escape
    test_looks.py about 1 minute pictures of the window and its panels against the last accepted ones
    test_language.py seconds Italian and back in each state: nothing left in the other language, nothing else changed
    test_sizes_and_docks.py seconds the window from 800×600 to 2560×1440; each dock floated, closed and brought back; the layout after a restart
    test_soak.py about 1.5 minutes; longer with LMS_SOAK_ROUNDS a long session in one window: nothing it holds may grow
    test_every_property.py about 1.5 minutes every property of every widget type, changed in the Properties panel
    test_every_example.py about 2 minutes every example started in the simulator and touched
    test_canvas_mouse.py seconds widgets dropped, moved at three zooms, resized from each handle, selected with the mouse
    test_typing_code.py seconds typing in the code editor: indents, suggestions, errors, the lists, read-only while running, random keys
    test_save_and_reopen.py about 2 minutes what is saved is what was in the window: examples and the monkey's work saved, opened in a new window, compared
    test_hard_texts.py about 1 minute long, quoted, escaped, foreign, right-to-left and emoji texts in every text property and as page names
    test_foreign_drops.py seconds files, folders and text dragged from outside, dropped anywhere: no harm
    test_console_flood.py about 30 seconds programs printing without pause into the terminal, the Output and the Device Console
    test_big_project.py about 15 seconds a project of 30 pages and about 2000 widgets: opening, pages, selection, moves, undo, a property, save and Start, timed
    test_mcp_and_window.py seconds an agent changing the project through MCP while the window has it open
    test_killed_while_saving.py about 3 minutes the IDE killed at random while it saves a project, a program and the board profiles
    test_keyboard_only.py seconds the IDE without a mouse: Tab, Alt and the letters of the menus, Ctrl+Tab; a name for every control
    test_monkey.py about 5 minutes a state; longer with LMS_MONKEY_STEPS clicks, drags, keys and menus at random anywhere in the window
    test_faults.py seconds the disk full, read-only folders, the runtime killed or hanging, a broken project, a board pulled out
    test_random_use.py about 1 minute; longer with LMS_RANDOM_EXAMPLES random sequences of what a person does

    What the suites share (the window, its states, the watcher that answers dialogs, the guard against real boards) is in tests/manual/sweep.py; the checks of the looks are in tests/looks.py, also used by the CI.

    Every action. Every menu entry and toolbar button is triggered as choosing it does, in five states of the IDE:

    • an empty project;
    • an example open, with two widgets selected and one change to undo;
    • the simulator running;
    • a program without pages running;
    • a board connected: on Linux the virtual board, reached with the real mpremote, so that Upload and Run, Stop, Autostart, Upload Files and the rest of the Device menu go through the real protocol; elsewhere a fake.

    Every dialog it opens is answered by a watcher, once with Cancel and once with OK:

    • a file dialog gets a file prepared for it;
    • a print dialog prints to a PDF, never to a printer;
    • links are not opened.

    After each action the suite checks:

    • no exception and no Qt warning;
    • no dialog left open;
    • the window still answers;
    • the project is still valid;
    • undo brings it back to where it was, redo does again exactly what the action did, and undo after redo brings it back once more.

    A new menu entry is tested without writing a test for it.

    The context menus are swept the same way: those of the canvas (on a widget and on the empty page), the project tree (a page, a widget, the Python Modules branch, a module), the Files panel (a program, a text file, a folder, the empty space), the board's files, the terminals and the code editor. Each menu is opened as a right click opens it, and opened again before each of its entries, since an entry can change what is under the pointer. Delete… of the Files panel moves files to a folder of the test, never to the trash of the PC. A menu that does not open is a problem, unless its widget is disabled, as the canvas is while the simulator runs.

    The report is written to build/manual/every-action/, one file per state and answer, with the dialogs each action opened and how long it took. Each run prints what changed since the last one: entries added or removed, other dialogs, a result that changed. That list is the place to start when trying the IDE by hand.

    The suite never reaches a real board: listing ports finds only the virtual board, and anything that would run mpremote towards another port, or open one, makes the test fail. Three entries are not triggered, and the suite says why: Exit, which closes the window, and the two Build Executable entries, which build for minutes in the background and are tested in tests/test_release.py.

    It checks that nothing breaks, not that the result is right: that is what the test suite and the self-test are for.

    Every shortcut. Each shortcut of each enabled action is pressed as keys, with the focus in the canvas, the project tree, the Files panel, the code editor, a field of the Properties panel (opened with a click, as a person opens it) and the terminals, with an example open, a program running and a board connected. Where the focus is not a text, the shortcut must reach its action; a text field or a terminal may take it on purpose (Ctrl+C copies the text, or stops the program), which the report notes. An ambiguous shortcut shows as the Qt warning it causes. The first run found that leaving the field of a property shared by several selected widgets with different values, without typing, gave all of them the value the field opened on.

    Every dialog. The actions and context menus of an example and of a connected board are triggered again, in English and in Italian, and every dialog they open is looked at before it is closed with Escape:

    • a picture of it goes to build/manual/every-dialog/<language>/, to look through by hand;
    • it must fit its screen, and need no more than 1024×700;
    • no label, button or column of a list may cut its text; no widgets may cover each other or stick out; no label may have a contrast below 3:1 on what is behind it;
    • Tab must reach every field and stay inside the dialog (in a group of radio buttons, the chosen one);
    • Escape must close it;
    • in Italian, no text may be left in English.

    Qt's own file, print and input dialogs are photographed but not checked. The first run found the Board Profile Manager wider than a small screen, with its columns cutting the names of the boards and, in Italian, a row of buttons wider than 800 pixels.

    Language. In each of the five states, Italian and back, twice: after the change to Italian nothing that has a translation may show in English, after the change back nothing may stay in Italian, and the project, the undo history, the selection and what runs are the same. The suite of every dialog also looks for English in the dialogs opened in Italian: it found Save, Cancel and Close in English everywhere, since the IDE did not load Qt's own translation.

    Looks. The window with an example open, then each panel and tab, in light and dark theme, English and Italian, at 1024×700 and 1920×1080. The pictures go to build/manual/looks/now/; the reference is build/manual/looks/accepted/, kept on the PC that makes it, since fonts differ between machines. A picture that changed is listed with its share of changed pixels, as something to look at, and does not fail the test; the first run, or LMS_LOOKS_ACCEPT=1, makes the reference. The checks that need no reference (text cut off, widgets covering each other, contrast) fail it. The dark theme needs a real display: offscreen skips it. The first run found the message of the Files panel without a folder cut in half when the panel is narrow.

    Sizes and docks. With an example open, the window at 800×600, 1024×700, 1366×768, 1920×1080 and 2560×1440: no text cut off, no widgets covering each other, no Qt warning. Each dock is floated and docked again, then closed and opened again from its entry of View, and must come back with its content. A layout changed by hand (a dock floated, one closed, another size) must be the same after the IDE is closed and opened again. It is worth running on a real display too: tools/manual_on_x.sh 1366x768 tests/manual/test_sizes_and_docks.py.

    Soak. In one window, round after round (30 by default): two examples opened in turn, a history of ten changes undone and redone three times, the simulator started and stopped. After five rounds to warm up, the Qt objects of the window, the visible windows, the child processes (zombies included) and the temporary folders of the IDE must not grow, and the memory of the process may grow by 40 MB at most; the numbers of each round go to build/manual/soak.json. Linux only. The first run found every project opened keeping the pages of the one before: 24 Qt objects and about 1.7 MB a round.

    Every property. For each of the 30 widget types, a widget on an empty page is clicked on the canvas, then each of its properties is changed through its field in the Properties panel: a number, a text, a choice or a colour typed and confirmed with Enter, a check box toggled with the space bar, an image or a font given as a file. The widget must hold what was typed, with no exception, no Qt warning and no error in the panel; at the end the real runtime must draw the page, and undo must bring back the empty page. About 340 properties.

    Every example. Each example is started with Run → Start; the middle of each widget of its first page is touched on the simulated screen, a few seconds are left to its timers, then Stop. Nothing may reach the Errors panel, and the Output may hold no Python error.

    The canvas under the mouse. In the real window: every widget type dropped from the toolbox must land where the pointer was, selected, and go away with one undo; every type dragged at zoom 1, 2 and 0.5 must move by what the pointer moved, keeping its size, as one undo step; each of the eight handles must resize as it should and never below the least size; a rubber band, Ctrl+click and a click on the empty page must select what they should, with the Properties panel following; the grid and the arrow keys must move as they say; a widget dropped on a panel must go inside it and move with it. The first run found a thin line growing to 8 pixels high when moved, or when pulled sideways by a handle.

    The code editor. With an example open, through keys and clicks: a double click on a widget opens its handler, lines are indented after a colon and Tab writes four spaces, the handler holds what the editor shows, and undo gives the old code back; suggestions come after lv., ui. and with Ctrl+Space, the arrows move in them and Enter writes the one chosen; a syntax error is underlined and said under the editor, Start lists it in the Errors panel and a double click there opens its line; every object and event of the two lists shows its stored code without changing the project; while the simulator runs keys change nothing and Stop and Edit gives the code back; 400 random keys (accents and emoji too) leave the editor and the project in agreement, and undo all gives the code of the start.

    Save and open again. Each example saved from the IDE and opened again must give the same project, and a second save must not change the file by a byte. Then, round after round, the monkey works on a project for a while; it is saved and opened in a second window, and the project and the canvas of each page (without the grid and the real preview, which are choices of the window) must be the same.

    Hard texts. Every text property of every widget type gets, pasted through the Properties panel, a text of 600 letters, quotes of every kind, backslashes and escapes, accents and other alphabets, Arabic, emoji, {name} and %s placeholders, spaces only; pages are renamed with the same texts. Each time the IDE must keep the text or refuse it with a message, and the MicroPython code must compile, the runtime must draw the pages and the C code must be generated. The first run found that a page or a widget could get a name longer than MicroPython takes ("name too long"), so that the project no longer started.

    Drops from outside. The IDE takes no files from the file manager; what is dragged there by mistake (an image, a font, a project, a program, a folder, two files, text from another application) is dropped on the canvas, the toolbox, the trees, the Properties panel, the code editor, the terminals and the window. Nothing may raise or change the project; the code editor may take dropped text as text, which undo takes back. The canvas shows a pointer that accepts files, then does nothing with them.

    Consoles under a flood. A program without pages prints without pause into the terminal of the simulator, an app prints from an LVGL timer into the Output, a file of the virtual board prints into the Device Console. For eight seconds each the window must answer within half a second, the memory grow by less than 80 MB and the consoles keep a bounded history; then Ctrl-C, or Stop, must stop the printing. The virtual board turns Ctrl-C into the signal a terminal would send, since its MicroPython does not read its input while a program runs. The first run found three things: a timer created in the general code crashed the simulator; the terminal took over 100 MB for its history; and the Device Console fell behind a board printing fast, without answering, and went on showing old output long after Ctrl-C.

    A large project. A project of 30 pages and about 2000 widgets, some inside panels, with a handler for every button, is opened in the window; opening it, showing each page, Select All, a move with an arrow key, undo and redo, a property typed in the panel, Save and Start are timed, each against a limit and against the last run on the PC (build/manual/big-project.json). The first run found that such a project did not start: mpy-cross and the runtime of the simulator ran out of memory. A move, undo and redo take close to a second each on it, because each change keeps a copy of the whole project: that is the speed work of the plan, not done yet.

    MCP and the window together. An agent changes the project through MCP while the window has it open and a person works on it. The window finds out when it saves, and asks: Cancel keeps both versions where they are, Reload shows the agent's change, Save a Copy keeps the person's version in another file, Overwrite keeps the person's; after each the window agrees with its project. An agent writing with a revision older than the person's save is refused; a widget the agent removed is gone from the canvas and the Properties panel after Reload; Start after a change by the agent asks first. Nothing found; the window learns of the change only when it saves, which can be long after.

    Killed while saving. A second process runs the window and saves without pause a large project, a program open in a tab and the board profiles; it is killed with SIGKILL at a random moment, forty times. Each time the project must open and validate, the program must be one of the versions written whole, and the profiles must load. The project and the profiles were already written through a copy and a rename; the tabs of the Files panel were not, and a failed write left the program empty: they are now written the same way.

    Keyboard only. Tab from the canvas must reach the toolbox, the project tree and the Properties panel, and the code editor from its lists; Shift+Tab goes back; the focus is caught nowhere, except in a terminal, where Tab belongs to the program as in every terminal. Each menu must open with Alt and its underlined letter, and Ctrl+Tab must go through the tabs. Every button, field and list must have a name a screen reader can say: the first run found the toolbox, the trees, the Properties panel, the Output and the code editor without one. The CI checks the names too, in English and Italian.

    Where the tests are blind. tools/mutation_probe.py [module] [count] makes small changes to a module, one at a time (a comparison turned around, and for or, a not dropped, a constant or a returned value changed), and runs the tests of that module for each: a change no test notices marks a line nobody checks. It works in a copy of the repository and writes build/manual/mutation/<module>.txt. Its first run, 25 changes in each of seven modules, found untested the checks of Rename Page, the names refused by New File, the check boxes of the Properties panel, Ctrl+click on the canvas, a container moved with its children, the tab stops and the background colours of the terminal; each now has a test, and the second run notices those changes. Most of what is still not noticed is drawing: margins, sizes, colours.

    Monkey. Thousands of events a person could cause, anywhere in the window: clicks, double clicks, right clicks, drags, the wheel, keys, and entries of the menus, with dialogs answered at random. After every step it checks that nothing broke (no exception, no Qt warning, no dialog left open, the window answers) and what must hold whatever came before: the project valid, widget names unique, a tab for each page, each canvas drawing its page, the Properties panel showing widgets that exist, the * of the title saying whether there is something to save. Each step is written to build/manual/monkey-<state>.log before it is made, so a crash of the process can be followed; LMS_MONKEY_SEED replays a run. Its first runs found Add Page giving a new page the name of one already there, after a deletion; its night runs found a crash when a tab of an old tab bar that Qt leaves over the Output panel was dragged. It finds by chance, so it pays to run it long: tools/monkey_night.sh [hours] [steps] runs it seed after seed, each run in its own process, and keeps the output and the steps of the runs that fail in build/manual/monkey-night/.

    Faults. Each one through the window, as it would happen to a person: the disk full during a save (the file on disk and the changes in the window are kept, no temporary file is left), a read-only project folder (Save, Start and New File… say so), a build folder that cannot be written, the runtime killed (the project is editable again and Start works), the runtime hanging (Stop ends it within seconds), the project changed outside (nothing is overwritten without a choice), broken project files (the open project stays), the board pulled out during an upload (an error, not a hang).

    On a real display. tools/manual_on_x.sh [WIDTHxHEIGHT] [suites] runs the self-test and the suites on Xvfb with the xcb platform instead of offscreen, so that real fonts, window activation and the dark theme are there; nothing appears on the screen of the PC. When a window manager is installed (openbox, fluxbox, icewm, xfwm4 or metacity) it starts it, and the sweeps also check that the window gets the focus back after each action. LMS_SCREEN_SCALE=2 scales Qt twice, as on a high-resolution screen.

    Random use. A hypothesis state machine chooses what to do next, through the window as a person would, with the self-test's driver: a widget from the toolbox, a click or a drag on the page, arrow keys, a property typed in the panel, Edit and Arrange entries, undo and redo, pages, the code of a handler, save and open again. After every step it checks that the canvas shows the widgets of its page, that the Properties panel shows what is selected, that the * of the title says whether there is something to save, that the project is valid and that nothing raised. At the end, undo all must give the project of the start, and redo all must give it back.

    When a check fails, hypothesis shortens the sequence as far as it can and prints it, with the state of the last ten steps and a line to replay it; a short sequence becomes an ordinary test. LMS_RANDOM_EXAMPLES (default 25) and LMS_RANDOM_STEPS (default 30) make a run longer; LMS_RANDOM_TRACE=1 prints the state after every step. On its first runs it found the Properties panel showing a widget that was not selected, in three ways: after New or Open, after Cut and Undo, and on another page.

    Board tests¶

    Tests marked board run only with --board PORT, and only with the owner of the board present, because they write to it. None is written yet.

    What the automated checks do not see¶

    • Whether the IDE is clear and pleasant to use. No check can say it.
    • Whether the IDE looks right. The suites compare its pictures with the last accepted ones and check sizes, cut text and contrast; whether a picture is good is for a person.
    • Real boards. The board code is tested against fakes and against a virtual board (tests/virtual_board.py: the runtime's MicroPython behind a pseudo-terminal, reached by the real mpremote, Linux only); touch, speed and the firmware's own behaviour are seen only on hardware.
    • The system around the IDE. The system's own file dialogs, dragging from the file manager, a real high-resolution screen: the checks run with Qt's own dialogs, offscreen or on Xvfb, where a window manager is used only if one is installed.

    How much of the code the checks run, measured on 17 November 2026 with coverage.py: 87 % of the lines of the user interface (copper_and_code_studio/ui) and 90 % of the whole package. The number says less than it seems. The bugs fixed on that day were in lines the tests ran: they came from order and timing, such as closing a window while a file was still being written to the board. This is why the suites run by hand drive the IDE through sequences of real actions rather than calling its functions one at a time.

    Rules for new tests¶

    • A test never touches the settings, recent files or board profiles of whoever runs it, and never opens a serial port; tests/conftest.py sees to the first and part of the second.
    • A test of the user interface should go through what a person uses (an action, a click, a key) when it can. A test that calls a method directly does not see how that method is reached. Device → Run File on Board… failed from its menu entry while its test, which called the method, passed.
    • A bug found by a suite run by hand also gets a test in the normal suite, so the CI keeps it from coming back.
